# T20261006-04 — RS485 고장 주입 → ERROR → `oroha_hw_recover` (M7)

- **조건**: 바퀴 띄움, 런치 `imu:=true` 정지 상태(명령 0). `inject_ff.py`: `/dev/oroha_md400`에 0xFF 바이트를 2 s(3520 B) 쓰기. 0xFF는 슬레이브 주소 255라 우리 MD400(1, 2)에 유효한 요청이 될 수 없다.
- **ERROR까지**: 주입 시작 15:37:48.05 → 쓰기·읽기 실패가 번갈아 이어짐(패치 0002 재시도도 실패) → 15:37:50.32 "read failed 5 times in a row" → controller_manager가 `oroha_base` 비활성(→ `unconfigured`), `joint_state_broadcaster`·`diff_cont` `inactive`. 실제 통신 끊김과 같은 경로이며, mock에서 손으로 내릴 때와 달리 컨트롤러도 내려간다.
- **복구** `oroha_hw_recover`: configure → inactive ok, activate → active ok(로그 "enabled (UI_COM=1 + START_STOP arm)"), 컨트롤러 2개 재활성 ok, `/joint_states` 0.00 → 종료코드 0. 소요 약 0.4 s(configure 0.32 s).
- **주행 확인**: 2 s 명령 0.1 m/s → L/R 27.2 / 27.4 rad/s(이론 27.5), −0.1 m/s → −25.7 / −25.1 rad/s(2 s 창 끝 값), 이후 0.
- 종료: 런치 SIGINT → 안전망 양쪽 정지 ok. `um7_node` 종료 traceback은 기존 외부 문제(T20261001-01).
- **판정**: 통과 / 종결. 실제 RS485 분리에서는 MD400이 마지막 명령을 유지하므로 E-stop을 누른 채 복구한다(`docs/operation.md`).
