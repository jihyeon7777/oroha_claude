# T20260929-07 — RS485 통신 두절 원인: MD400 수신 잠김 (ros2_control 없이 재현)

- **조건**: 바퀴 띄움. 런치 없이 `oroha_bus_probe`(신규, `src/oroha_tools/oroha_tools/bus_probe.py`)가 `/dev/oroha_md400`를 직접 열어 두 MD400을 폴링하고 모든 트랜잭션을 기록. `steps` = 램프 0.2 s → 500 rpm 4 s 유지 → 램프 다운 → 1 s 정지를 전진(id1 +, id2 −)·회전(둘 다 +)으로 번갈아 반복. r1~r5는 Pico(`power_node` + bag `data/tests/T20260929-07/bag_r*`) 동시 기록. 코드: 961f050 + 패치 0001(미커밋, `versions.yaml`·`uncommitted.diff`).
- **선행**: 패치 0001 적용 런치에서 사각 경로 1회차 FAIL(`R20260929-150806-square`, turn4 출발 t≈44 s). 이번엔 **오른쪽(id1)이 먼저** 무응답, status/status2는 끝까지 0(알람 없음), 두 MD400 위치 카운터는 **리셋되지 않음**(직접 읽기 R 60757 cnt ≈ 12710 rad, L 2468 rad = 마지막 발행값) → 전원 차단 가설과 불일치.

- 잠김 동안: 잠긴 MD400은 **읽기·쓰기 모두 무응답**(`short read: got 0`), 새 속도 명령도 **실행 안 함**(잠기기 직전 명령 106 rpm으로 계속 회전, 위치 +331 cnt/6.4 s). 다른 MD400은 정상.
- 복구 3건 모두: 잠긴 장치로 가는 요청 **바로 앞에 다른 장치 통신이 없고 약 100 ms 휴지**(직전 실패의 타임아웃)가 있었다. 잠김 루프에서 잠긴 장치 요청은 항상 다른 장치 응답 직후(간격 ≈ t3.5 = 2 ms)였다.
- 잠김 직전: 잠긴 장치의 쓰기 응답 지연이 평소 14 ms → **26 ms**(r0·r1 모두 정지 상태에서 첫 비영 명령, 출발 순간). r3은 램프 중.
- Pico: 잠김 전후 버스 전압 28.2 V 변화 없음, 잠긴 쪽 전류는 저속 구동 수준 유지 → 전원 문제 정황 없음.
- 빈도(t3.5 = 2 ms, 매 주기 쓰기): 4회 / 약 750 s.

## 해석

MD400(fw v8.6)이 간헐적으로(모터 출발·감속 순간에 몰림) **수신 동기를 잃고, 다른 장치 통신 직후 짧은 간격으로 오는 요청을 계속 버리는 상태**에 빠진다. 휴지 뒤 요청 하나를 받으면 풀린다. ros2_control 플러그인은 한 주기에서 같은 순서(L 읽기→R 읽기→L 쓰기→R 쓰기)로 번갈아 보내므로 잠긴 장치 요청은 항상 다른 장치 통신 직후 → 5회 연속 실패 → ERROR. T20260929-05·06의 "왼쪽 무전력·카운터 리셋" 정황은 이 결과와 맞지 않아 재검토 대상(당시 자료를 이 관점으로 다시 볼 것).

## 대책(시험 중)

1. 프레임 간격 5 ms(`--ifd 0.005`)로 잠김 자체가 줄어드는지 — r4·r5(각 540 s).
2. 플러그인 패치 0002: 실패한 장치를 **즉시 한 번 재시도**(타임아웃이 휴지 역할) + `inter_frame_delay` 파라미터 → 런치 사각 반복으로 검증.

- **판정**: 원인 재현·기전 확인 / 열림(대책 검증 전).
